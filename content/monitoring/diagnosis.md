## 진단의 시작

**환경(dev/prod) → 서울 리전 → 시간 범위**를 맞춘다. 서비스 자체가 안 되면 Nginx·백엔드·최근 배포 상태를 먼저 본다. 정상 서비스에서 관측 데이터만 사라졌다면 끊긴 경로를 찾는다.

## 증상별 첫 확인

- **로그만 없음:** 로그 그룹·최근 정상 요청 → Docker awslogs 설정·권한.
- **메트릭만 없음:** ADOT 실행·오류 로그 → 수집 엔드포인트 → Query Studio 라벨·최신 시각.
- **Query Studio에는 있는데 대시보드만 빔:** 패널 쿼리·환경 필터·시간 범위.
- **경보는 ALARM인데 Discord에 안 옴:** 경보 작업 이력 → SNS 구독 → Lambda 실행 로그 → Discord.

5xx 그래프가 비거나 경보가 정상이어도 수집 중단일 수 있다. **전체 요청 데이터의 최신성**을 함께 확인한다. 배포 뒤 수집기가 사라졌다면 `.env`의 `COMPOSE_PROFILES=metrics`와 배포 결과를 확인한다.

## 기록하고 조치하기

재시작으로 증거를 지우기 전에 당시 로그·컨테이너 상태·메모리를 남긴다. 메모리는 `free -h`의 available과 `vmstat 1 10`의 지속적인 si·so를 함께 읽는다. swap 사용량 하나만으로 장애를 판단하지 않는다.

```text
언제 / 어느 환경 / 어떤 사용자 영향:
당시 로그·메트릭:
확인된 원인:
조치와 시각:
같은 지표로 확인한 조치 전후:
```

스프린트 제출에는 실제 장애·성능 문제 1건의 기록이 필요하다. 아직 선정된 사건은 없다. 모의 실습을 실제 장애 기록으로 제출하지 않는다.
